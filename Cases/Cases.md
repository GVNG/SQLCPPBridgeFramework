## How to use these examples

Each example is intentionally self-contained and focuses on a single feature of SQLCPPBridge. If you are looking for a specific capability (such as inheritance support, smart pointers, STL containers, or optional values), start with the corresponding example listed below.

The examples are ordered approximately from basic object persistence to more advanced mapping scenarios.

# Cases

This directory contains a collection of self-contained examples demonstrating individual features of SQLCPPBridge. Each case focuses on a particular aspect of object persistence, schema mapping, or framework behavior.

| Case | Demonstrates | Highlights |
|------|---------|------------------|
| **Example 1** | Demonstrates persistence of an object graph containing nested objects and collections. The example stores a root object together with related entities and attached objects, showing automatic traversal of object relationships during serialization. | Uses three mapped tables (`main`, `related`, and `attaches`). Saving the root object automatically persists all referenced objects. Suitable as the introductory example of recursive object persistence. |
| **Example 2** | Demonstrates inheritance support. Illustrates objects derived from different base classes can be mapped and persisted while preserving inherited fields. | Requires mapping every participating type. Useful when persistent classes share common base classes. |
| **Example 3** | Demonstrates persistence of a simple standalone object without related tables. Serves as the minimal mapping example. | Uses a single mapped table and is intended as the simplest possible configuration. |
| **Example 4** | Demonstrates persistence of an object that owns a collection of owned entities. Illustrates one-to-many relationships are represented. | Two mapped tables are used (`main` and `member`). Owned entities are created and restored automatically together with the owning object. |
| **Example 5** | Demonstrates custom serialization logic for types that cannot be handled using the default mapping rules. | Does not rely solely on standard table mapping. Intended as an example of extending framework behavior for user-defined data representations. |
| **Example 6** | Demonstrates attached (embedded) objects stored together with the owning entity. | Uses separate mappings for the primary object and its attached object. The attachment lifecycle is managed automatically by the framework. |
| **Example 7** | Demonstrates persistence of a standalone complex object with custom data layout. | Uses a single mapped entity. Useful as a reference for mapping larger objects without external relationships. |
| **Example 8** | Demonstrates mapping of an object whose state consists primarily of value members rather than object references. | Single-table example focused on field mapping rather than relationships between entities. |
| **Example 9** | Demonstrates persistence of owned entities independently from a dedicated root entity. | Illustrates collections of mapped objects can be stored and restored directly. Useful for reusable child entities. |
